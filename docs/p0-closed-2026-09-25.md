## The canary chain, as it actually ran

1. `lisa-core canary send` (coder's new CLI) sent 4 nonces (gateway/embed/rerank/small) at 09:24 —
   each INSERTed into `ops.canary`, content `LISA-CANARY-<32 hex>`.
2. Fleet searched the GPU host for all 4 nonces: the LLM gateway dump dir, the LLM gateway container logs,
   sglang-27b container logs, docreader containers, host logs — **zero hits. Nothing leaked.**
3. Results POSTed to `/v1/ops/canary-report` (found=false ×4) → gate recomputed →
   **`privacy_gate = open`**. Health page (authenticated, over the tailnet URL) shows
   "D3 已确认，所有服务 canary 通过".
   Note: an ops-role token was needed; `pair` only mints node/client, so the fleet promoted a
   token via SQL (`UPDATE ops.tokens SET role='ops'`) — **the key-provisioning gap from F4 is
   still open: there is no documented/automated way to mint an ops token. Coder should add a
   `lisa-core pair --role ops` path or a CLI command for it in P1.**
   Also: the earlier 09:10 canary batch was the coder's own run (reported 09:15) — the flow was
   already exercised once before the fleet's independent round.

## Auth hardening, verified adversarially (nice work by the coder)

During the ops-token hunt the fleet probed the guards and all behaved as designed: node token →
403 "node 令牌只能访问 node/executor 端点"; client role → 403 role-forbidden; missing Origin →
CSRF error; wrong nonce → 404 UNKNOWN_NONCE; unauthed health page → 401. No bypass found.
