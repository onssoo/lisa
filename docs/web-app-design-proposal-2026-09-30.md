# lisa Web App — 设计提案（PWA）

> 状态：**提案**（design proposal）。作者：协调人（DSH），2026-09-30。
> 权威链：本文 → `design.md` / `contract.md` → 实现。**本文不直接作为编码依据**；评审后再合入 design/contract。
> 起因：owner 要求 —— 「digest 只是编辑过的当日事实合集；我需要一个 UI，把 digest 和更多内容**生动地**呈现在网页上，像一个 web app」。

---

## 0. 一句话

lisa 的网页**不是 dashboard，是一本可以翻的「每天一页」**。它是 lisa 唯一的人机界面，主要形态是 **tailnet 内、手机 Safari 上的 PWA**。

---

## 1. 最重要的判断：生动的 UI 是「数据问题」，不是「渲染问题」

现状：`/today` 把 `memory.digests.summary_md` 塞进一个 `<pre>`。**再怎么美化，那也是一堵散文墙。**

要「生动」，页面必须渲染**对象**，而不是段落：

| 对象 | 页面上长什么样 |
|---|---|
| **卡片 card** | 一句话 + 截止 chip + 溯源 + **已经备好的下一步**（一键执行） |
| **事件 event** | 时间 · 来源 · 谁 · 内容（时间轴） |
| **承诺 commitment** | 状态 · due · 「挂满 7 天已问过一次」 |
| **数据源 source** | 新鲜度：「iMessage 已 3 小时未更新」 |

**这些对象现在都不存在。** `memory.cards` / `memory.commitments` / `memory.focus` 属于 **P2.1**，表还没建（迁移 `0003_p2_pages.sql` 未落），库里是空的。而 markdown digest 是**日志/归档**，不是 UI 的数据源。

⇒ 真实依赖链（这也是本提案的核心结论）：

```
结构化的「一天」数据 (P2.0 → P2.1)
        → 页面 JSON API（每段带 as_of，contract X6）
                → web app（前端只是最后一公里）
```

**所以「做个好看的前端」不是一个可以最后补的活**；UI 的生动程度被上游数据决定。

---

## 2. 定位：一本书，不是一块仪表盘

依据 `requirements-p2-v2.md`：lisa 的基本单位是**天**，这本书从上线那天开始写、不回填。于是：

- 主视图 = **今天这一页**
- 浏览 = **翻书**（昨天/明天/任意一天/周页）
- 最重要的使用时刻 = **早上 30 秒**（手机上）看完「昨日回顾 + 今日卡片」

**唯一的 KPI：早上在手机上 30 秒内看完回顾和卡片。** 所有设计取舍服从这一条。

## 3. UI 如何体现已有原则（requirements T1–T5 / X12 / X6）

| 原则 | UI 上的具体表现 |
|---|---|
| **T1 以此刻为准** | 页面在**打开那一刻**计算：过了的日程显示「已过」、截止显示「还剩 2 天」。每次刷新都不一样，**永远不会是昨晚写死的文字**。 |
| **T2 模型不写相对时间** | 库里只存绝对时间；「昨天 21:30」「3 小时前」全部由**客户端渲染层**算出来。 |
| **T3 内容注明截至何时** | 每一段都带 `as_of`（「采集截至 14:32」「判断截至今晨 04:40」）；数据源缺失就直接写出来。**诚实 > 好看。** |
| **T4 两个时间** | 事件同时显示发生时间与「补记于 X」；晚到的数据落在当天页面的补记区。 |
| **T5 合上的页只追加** | 已合页不可编辑；补记以追加形式出现，视觉上与正文区分。 |
| **X12 引用可校验** | 每个 `[F4]` 是**可点**的 chip → 打开源事件抽屉（原文 + 时间 + 来源）。**能被检查才值得信任。** |
| **X6 每段 as_of** | API 层就返回 `as_of`，前端不用猜。 |

## 4. 信息架构（5 + 1）

| 屏 | 角色 | 现状 |
|---|---|---|
| **今天** `/today` | 当前这一页（早上卡片优先，晚上记录优先） | ½（只有 markdown） |
| **书** `/day/YYYY-MM-DD`、`/week/YYYY-Www` | 翻任意一天/一周 | ❌ 未建 |
| **待处理** `/pending` | 审批台：逐条决定提案（批准/忽略/放下/执行） | ❌ 空壳 |
| **记忆** `/memory` | brain：人物/项目/地点，反向列出提到它的每一页 | ❌ 未建 |
| **问** `/ask` | 有据可查的聊天，每句话可点回源 | ❌ 未建 |
| 健康 `/health` | 运维视图（新鲜度/闸门/canary） | ✅ 已有 |

导航：底部 tab（手机）→ 今天 / 书 / 待处理 / 问；健康与记忆收进二级。

## 5. 「今天」这一页的构成（四部分 + 按时段重排）

`requirements-p2-v2.md` §3 的四部分，**内容固定，顺序随打开时刻变化**：

| 部分 | 内容 | 早上侧重 | 晚上侧重 |
|---|---|---|---|
| 昨日回顾 | 两三句，只写与今天有关的延续 | ✔ | |
| 今日卡片 | 3–5 张需要动手的卡片（+ 已备好的动作） | ✔ | ✔ |
| 今日记录 | 今天发生了什么（时间轴） | | ✔ |
| 明日预告 | 明天的日程与要提前准备的事 | | ✔ |
| 页脚 | 各数据源状态 + 截至时间（T3） | ✔ | ✔ |

> 这个「按时段重排」**本身就是设计**：同一个 URL，早上和晚上是两种阅读体验。

## 6. 组件清单

1. **DayHeader** — 日期（大字）+ 状态徽章（open/ready/digested）+ as_of + 日/周切换。
2. **DaySpine** — 左右翻页（‹ 昨天 / 明天 ›），支持手势滑动。
3. **CardList** — 卡片（≤5 + 「另有 N 项」折叠）：
   - 一句话标题、`due_at` chip（客户端算相对时间）、kind 图标（commitment/health/change/prep）
   - 展开：溯源列表 + **已备好的下一步**（一键批准）
   - 标记行：已处理 / 忽略 / 放下 / 执行
4. **Timeline** — 今日记录：左侧时间轴，每条 = 来源图标 + 谁 + 内容摘要；点击展开原文。
5. **SourceStrip** — 页脚新鲜度条：每个源一个 pill（complete/partial/stale/missing/blocked），带「X 小时未更新」。
6. **CitationChip** — `[F4]` → 打开 SourceDrawer（该事实的源事件原文）。
7. **CommitmentBadge** — 承诺状态（open/done/dropped/snoozed + 挂了多少天）。
8. **PreviewCard** — 明日预告 + 提前量标签（1/3/7 天）。
9. **AskThread** — `/ask` 的消息流，每条引用可点、可回滚。
10. **BrainPage** — `/memory` 条目：compiled truth（汇总事实）+ append-only 时间线 + 提到它的每一页。

## 7. 视觉与交互方向（待 owner 定，见 §10）

- **手机优先**，大触控目标，暗色模式优先（夜间/清晨使用场景）。
- **书感**：衬线标题 + 克制的色彩 + 「页」的边界感；不是数据仪表盘。
- **引用即链接**：可信度来自「随手能查」。
- **诚实的空白**：没有数据就写「iMessage 已 3 小时未更新」，不用好看的占位图糊弄。
- **PWA**：可安装、离线可读已合页（缓存最近 N 天）、`manifest.json` + service worker。
- **无 LLM 参与渲染**：页面打开必须**瞬间**（毫秒级），所有智能都在夜间完成后落库。

## 8. 技术架构（建议）

### 8.1 后端：结构化 JSON API
```
GET /api/day/{YYYY-MM-DD}   → {day, state, as_of, parts:{review,cards,record,preview}, coverage:[{source,state,as_of,watermark}], commitments:[...]}
GET /api/days?from&to       → 书目（每页一句摘要 + 状态）
GET /api/cards/{day}        → 卡片 + 提案
POST /api/cards/{id}/mark   → {action: done|ignore|drop|execute}
GET /api/ask?q=...          → SSE，带引用
GET /api/source/{kind}/{id} → 源事件抽屉内容
```
**每个 section 都带 `as_of`**（X6）——因为相对时间是客户端的事。

### 8.2 前端：服务端首屏 + 轻量水合，**不做重 SPA**
理由：单人、内网、永远本地——**健壮与快**胜过框架新鲜度；而且要保留「没有 JS 也能读」的下限。
- 首屏由 Jinja 渲染（无需 JS 即可读）
- 客户端只负责三件事：**相对时间计算（T1/T2）**、**动作按钮**、**溯源抽屉**
- 断网时读已合页（service worker 缓存）

> 若 owner 更想要「App 一样顺滑」的翻页/手势/离线，再考虑升级为小体量客户端渲染；这是一个**可后置**的决策，不阻塞 P2.1/P2.2。

## 9. 依赖与构建顺序（映射到 P2 迭代）

| 步骤 | 内容 | 依赖 | 产出「可见」的东西 |
|---|---|---|---|
| **P2.0** 地基 | `0003` 迁移（cards/commitments/focus + ingested_at 索引）、`archive/YYYY/MM/DD.md`、T1–T5 落地、roles 配置 | 进行中 | markdown 归档可读 |
| **P2.1** 今天这一页 | 卡片 + 预生成提案 + 审批台 + 承诺链 + 关注清单 | P2.0 | **卡片真正出现 → UI 第一次「生动」** |
| **P2.2** 昨天与明天 | 预告/提前量、前后翻页、周页、预告核对、白天增量 | P2.1 | **翻书**（`/day`、`/week`） |
| **P2.3** 记忆页 | `/memory` 查看/修正/删除 | P2.2 | brain 可见 |
| **P2.4** 聊天 | `/ask` + 引用校验 + 评测集 | P2.1 | 有据可查的问答 |

**结论：web app 不是独立项目，它就是 P2.1–P2.4 的界面层。** 建议在 P2.1 就把 `/api/day` + 页面骨架建好（否则 P2.2 的翻页要返工）。

## 11. 非目标（沿用 requirements §14）

- 不做原生 App（Safari + PWA，tailnet 访问）
- 不做多用户、不做社区技能市场、不做用户自定义定时任务
- 不做浏览器 agent / 云端电脑；不代发消息或邮件
- UI 不承担计算：不在渲染时调用 LLM
- 健康数据（睡眠/HRV/步数）是 P3 候选，不进 UI

---

## 12. 最小可验证切片（如果要先看到东西）

若想尽早看到「一个像样的 UI」，建议的**最小切片**（不改变上面结论）：

1. `/day/YYYY-MM-DD` 页面：**四段卡片式排版**（把现有 digest 的 `## 今天 / ## 重要的事 / ## 决定与承诺 / ## 待你处理 / ## 覆盖情况` 解析成结构化段落）
2. 引用 `[Fn]` → 抽屉显示源事件原文（X12 的最小实现）
3. 页脚 **SourceStrip**（数据源新鲜度）
4. 手动切日（‹ ›）+ `/days` 书目

这四件事能让 digest「活起来」，**且不会因为 P2.1 落地而返工**——因为它们渲染的是稳定对象（段落/引用/来源/日期）。
