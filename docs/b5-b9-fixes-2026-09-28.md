## B5 — reader Apple-epoch 转换 + 存量 raw.events 迁移

**reader 转换已存在**（协调人 grep 只查了 `*.py`/`*.sql`，漏了 Swift）：
- `node/Sources/LisaNode/Readers/ImessageReader.swift:220` `date(fromApple:)`：
  `raw > 1e12` 视为纳秒，否则秒，均相对 2001-01-01；
- `node/Sources/LisaNode/Time.swift:9` `appleEpochOffset = 978_307_200`（2001−1970）。
- 引入于 `d88b39f`（P1 初版），早于 B5 缺陷报告；`65b1785` 只修了 JOIN key /
  `uncanonicalized_id` / `date_edited=0`。

**存量数据已干净**（改前 SELECT 样本，生产库 `lisa@backup-host`）：
```
215 行 imessage，0 行 day='2001-01-01'；
day 分布 2026-08-30 .. 2026-09-25，全部为真实短信内容（如「1024 MB 中國內地澳門
共享漫遊數據 已儲存到你的儲…」「【佛山市应急管理局、气象局】…中秋假期…」）。
```

**迁移**：`core/migrations/0002_imessage_apple_epoch.sql`
- 守卫 `source='imessage' AND occurred_at < '2001-01-01'`：chat.db 不可能存
  2001 年以前的消息，落在 1970–2001 区间的 imessage 行必然是把 Apple-epoch
  秒数当 Unix 存的坏行；
- `occurred_at += 978307200s`，`day` 按生产值（Asia/Shanghai、04:00 rollover）
  重算（纯 SQL 拿不到 config 的 tz_timeline / day_rollover）；
- 幂等：修好的行落在真实区间，不再命中守卫。生产数据干净，实际为 no-op 安全网。

**测试**：`core/tests/integration/test_imessage_apple_epoch.py`
- 坏行（1995-09-18 09:16:43.305Z，即 2026-09-18 的 Apple-epoch 值当 Unix 存）
  → 迁移后 2026-09-18T09:16:43.305Z、day=2026-09-18；
- 干净行不动；非 imessage 行即使落在坏区间也不动；重跑幂等；
- 全干净库 no-op（对应生产现状）。
