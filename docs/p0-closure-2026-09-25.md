### Two findings for the reviewer (gateway security posture)

1. **The gateway does not authenticate keys.** Any Bearer string is accepted (tested: a fake key
   returns 200). `agents.yaml` is a naming roster only — `server.py` no longer consumes it; the key
   lands in telemetry purely as an `agent_id` label. Consequences: there is no revocation mechanism,
   and "lisa's own key" is a tag, not a credential. Acceptable inside the tailnet (single-user,
   owner-controlled machines), but if real credentials are ever wanted, the check must be added in
   the LLM gateway itself — a non-trivial change worth a decision at P1 time.
2. **Keychain ACL blocks headless access.** `security find-generic-password` from an SSH session
   returns rc=36 ("user interaction not allowed"); with `security unlock-keychain` run first in the
   same session it works. The launchd-run worker has no one to unlock for it — **currently the
   worker would fail to read the key with the same rc=36.** Mitigation options for the coder (P1
   item): have the LaunchAgent plist run `security unlock-keychain` with the login password from a
   protected file (weak), or expose the key via `LISA_GATEWAY_KEY` in the plist's environment from a
   root-owned 0600 file, or run the worker as a launchd agent in the owner's GUI session. Needs a
   decision; flagged for the next build round. (Not a P0 blocker: the gate is closed, so no worker
   LLM call happens yet — but it WILL bite the moment the gate opens.)
